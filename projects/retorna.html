01 / CONTEXT

The problem

A loyalty platform must do more than calculate a balance. Purchases and redemptions can arrive twice, requests can overlap, and different stores can use different policies. In those situations, a visually correct dashboard does not prove that the data is correct.

The central engineering requirement was to protect points history and business invariants when integrations retry operations or customers attempt concurrent redemptions.

03 / DESIGN

Engineering decisions

01

Idempotent operations

A repeated request should not create a second redemption. The redemption service checks external identifiers and handles conflicting retries.

02

Concurrency control

Transactional boundaries, row locks and PostgreSQL advisory locks guard balance-changing operations when requests arrive simultaneously.

03

Modular boundaries

Domain services centralize loyalty operations so the REST API and server-rendered interface do not have to duplicate rules.
